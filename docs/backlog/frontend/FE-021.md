# FE-021 — Calendar + Meeting Flow

**Epic:** CALENDAR  
**Priority:** P0  
**Status:** NOT_STARTED  
**Parallel-safe:** NO — depends on FE-004, FE-005, FE-019  

---

## Product Requirement

Meeting request discoveries offer "Find a time." This triggers a calendar check, presents available slots, the user selects one, the event is created (Level 2 approval), an email response is drafted, and the user approves sending (Level 3 approval). Calendar connection is requested contextually — not during onboarding.

## Current State

No calendar flow exists. This is entirely new.

## Target State

- Meeting discovery "Find a time" action triggers calendar flow
- Calendar connection requested contextually if not yet connected
- Slot selection → event creation → email draft → user approves send
- All agent states via `AgentActionPanel`
- Translated in EN and ES

## Scope

**Create `src/hooks/useCalendarStatus.ts`:**
```typescript
// GET /calendar/status → { connected: boolean }
```

**Create `src/hooks/useAgentAction.ts`:**
```typescript
function useAgentAction() {
  // POST /agent-actions/availability { discoveryId } → AgentAction
  // POST /agent-actions/:id/approve { selection? } → AgentAction
  // POST /agent-actions/:id/send → AgentAction
  // Returns { action, state, trigger, approve, send }
}
```

**Create `src/components/CalendarConnectPrompt.tsx`:**
```tsx
interface CalendarConnectPromptProps {
  discoveryId: string;
  returnPath: string;
}
```
- Wrapped in `<RequiresPro feature="calendarActions">`
- If Free: shows Pro upgrade prompt
- If Pro + not connected: "Connect Google Calendar so Detective can find available times" + [Connect Calendar] button
  - Store `{ returnPath }` in sessionStorage under `calendar-return-context`
  - Button → `window.location.href = VITE_API_BASE_URL + '/calendar/connect'`
- If Pro + connected: renders nothing (parent proceeds with action)

**Handle calendar OAuth return:**
- Backend returns to `returnPath` stored in sessionStorage
- In `DiscoveryDetailPage` (FE-014): on mount check if `?calendar_connected=true` and auto-trigger the "find_time" action

**Create `src/components/MeetingActionFlow.tsx`:**
Wraps `AgentActionPanel` with calendar-specific state management:

```
idle → [user clicks "Find a time"]
  ↓ POST /agent-actions/availability
thinking → [polling for proposal]
  ↓
proposing → [render time slots as selectable list]
  ↓ [user selects slot]
approving → [AgentActionPanel Level 2: "Create meeting [day] at [time]?"]
  ↓ [user clicks Confirm]
  ↓ POST /agent-actions/:id/approve { selectedSlot }
executing → "Creating calendar event..."
  ↓
verifying → "Confirming..."
  ↓
done → "✓ Event created: [day] at [time]"
     → Show draft email response
     → [Send response] button (Level 3 AgentActionPanel)
       ↓ [user approves]
       ↓ POST /agent-actions/:id/send
       executing → verifying → done: "✓ Response sent"
failed → [error + retry]
```

**Render in `DiscoveryDetailPage`:**
- `find_time` action → `<MeetingActionFlow discoveryId={id} />`
- Wrapped in `<RequiresPro feature="calendarActions">`

**Timezone / time formatting:**
- Slot times: use `formatMeetingTime(date, locale, timezone)` from `src/lib/formatting.ts`
- English: "2:00 PM" / Spanish: "14:00" (locale-appropriate)

**Email draft language note:**
- The email draft content is AI-generated by the backend
- Backend should infer the draft language from the source email's language, not the UI locale
- Frontend renders the draft as-is (do NOT translate it)

## Agent Notes

- The email draft is AI-generated content — render it verbatim. The backend infers draft language from the email conversation, not the UI locale. Do NOT translate it or pass through `t()`.
- `AgentActionPanel` state is managed in `MeetingActionFlow` — don't let `DiscoveryDetailPage` become a giant state machine.
- Polling for the agent action proposal: the `POST /agent-actions/availability` may return an in-progress action. Poll `GET /agent-actions/:id` until `state === 'proposed'` before showing the proposal.
- The sessionStorage key for calendar OAuth return context is separate from the upgrade context: use `calendar-return-context`, not the billing upgradeContext.
